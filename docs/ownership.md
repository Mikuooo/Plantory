# 代码所有权与软责任

Plantory 使用 `.github/CODEOWNERS` 路由评审请求，并用本文件定义维护责任。
所有权是责任入口，不是修改权限边界，也不自动构成合并阻断条件。

## 当前责任人

| 范围 | 责任人 | 主要责任 |
| --- | --- | --- |
| 仓库默认、发布与安全 | `@Mikuooo` | 范围判断、风险升级、发布与回滚完整性 |
| `apps/mobile/` | `@Mikuooo` | Expo/React Native 运行时、移动端体验与原生验证 |
| `packages/`、`services/` | `@Mikuooo` | 共享契约、服务边界与兼容性 |
| `docs/` | `@Mikuooo` | 产品不变量、架构、测试和执行证据的准确性 |
| `.github/`、`scripts/` | `@Mikuooo` | CI、质量门、自动化脚本和供应链配置 |

新增协作者或团队后，应在同一个变更中更新 CODEOWNERS、本表和
`quality/document-freshness.json`，避免 GitHub 路由与文档责任分离。

## 责任约定

责任人应维护所辖边界的源文件和验证入口，及时判断跨边界风险，并确保变更
包含与风险相称的测试、运行证据、文档和回滚说明。发现缺陷或陈旧契约时，
责任人负责确认归属和下一步，而不要求亲自完成所有实现。

作者可以修改任何有权限的路径。提交评审时应通知匹配的 CODEOWNERS；作者
同时是责任人时，应在 PR 检查项中记录自审。责任人未响应不会自动豁免质量
门，也不会永久阻塞工作；在没有强制审批规则时，作者可以在完成仓库门禁、
记录风险与未覆盖范围后继续交付。

## 强制边界

当前不启用 required CODEOWNER review，也不以 CODEOWNERS 替代服务端权限、
分支保护、测试或安全审查。涉及秘密、数据破坏、生产发布、授权模型或不可逆
迁移的变更，仍须按对应安全和交付规则取得明确批准。

## 维护与升级

- CODEOWNERS 必须保留覆盖全仓库的默认规则。
- 文档 freshness registry 的 owner 必须是 CODEOWNERS 中存在的 GitHub handle。
- owner 变更需要确认新责任人具有仓库访问权限并愿意承担维护责任。
- 当团队规模和审查稳定性足够时，再单独评审是否启用 required review；本制度
  本身不授权开启强制门禁。
